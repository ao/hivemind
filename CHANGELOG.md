# Changelog

Notable changes to hivemind, newest first. Versions follow [Semantic Versioning](https://semver.org). A release is cut by pushing a `v*` tag; its notes are the matching section below.

## [2.2.0] - Unreleased

### Added

- A server can advertise a DNS name, which is now the recommended set-up: a server restored on a machine with another IP address then needs only the name's record updated, and the workers reconnect without joining again, with their certificates and containers. `serve --advertise <name>` binds the cluster listeners on the address of this machine that the name resolves to, and refuses a name that resolves to none of them. `--cluster-addr <ip>` binds that address instead, for a name whose record does not lead to this machine yet, as during a restore, or one that resolves to a NAT in front of it; `serve` logs a warning while the name resolves elsewhere. The server's certificate names the advertised address and the bound one. See [docs/concepts.md](docs/concepts.md#the-servers-address) and [docs/backup.md](docs/backup.md#replacing-a-lost-server).
- `hivemind node set-server <address>` moves a stopped worker to its server's new address, for a cluster that advertises an IP address. Before it changes `node.json`, it checks from the worker that the address serves a certificate from the worker's own cluster CA that names the address, and that the server accepts the worker's certificate and answers a node API request for its node. Another cluster's server, a certificate for another name, a server that refuses the worker, a removed node, an address that does not answer and the join port are refused with what was found, and `node.json` is left as it was. It also moves a cluster from an IP address to a DNS name. See [docs/backup.md](docs/backup.md#at-a-new-ip-address).
- `serve` logs, when the server's address changed since its last start and the store has workers, a warning that names `hivemind node set-server <advertise>` when the workers dial the advertised IP, and a note when they dial a name.
- `hivemind nodes` shows, on the server's row, the address the workers dial after the node's own when `--advertise` gives another, as `172.31.19.207 (hivemind.accept.test)`; `GET /v1/nodes` and `nodes --json` have it as the server node's `advertise`. A worker registers the server address in its `node.json`, which `GET /v1/nodes` shows as its `dials` and the store keeps (schema version 16). The warning `serve` logs when its address changed names, in `dial_old_address`, the workers that registered the old IP address, also when `--advertise` is a DNS name and some workers still dial the old IP. In the third acceptance run nothing in the CLI showed the advertised name, and the warning could only count the workers. A worker of an earlier build sends no `server` field and registers as before. A server that refuses the field gets the registration again without it, and then, if it refuses that too, as one older than 2.2 does the address, without the address as well.
- `scripts/integration-newaddr.sh` restores a server on a container at another IP address twice: for a cluster that advertises a Docker network alias, which moves to the new container 30 s after it starts, with a router on every node and a routed app on the workers, and for one that advertises an IP address, whose workers are moved with `set-server` after it refused another cluster's server, a name the certificate lacks, a port where nothing listens and a running worker. In both, the workers keep their node IDs, certificates and containers, the apps converge, and no replica runs twice. Then the old server's container starts again with its old store: by name, with the alias moved back to it, both workers refuse it and keep their containers, and take the restored server again once it is back; by IP, `set-server` to it is refused. CI runs it.
- `hivemind compose convert`, `deploy` and `delete` read a Docker Compose file and make one app of each service. The CLI does the conversion; the API is unchanged. The keys read are `image`, `command`, `environment`, `ports`, named `volumes`, `deploy` (`replicas`, `resources` and `restart_policy`), `healthcheck` and `restart`, with anchors, merge keys, `x-` extensions and `.env` interpolation. Any other key is refused with its path and a reason, and every refusal is listed in one error. A port with no address is published on `127.0.0.1`, where Compose publishes on every interface, and a note on standard error says so for each such port. An unset variable with no default is an error rather than an empty string. Apps do not find each other by service name. `deploy` validates every app before it sends any, and `--prefix` names the apps `<prefix>-<service>`. See [docs/compose.md](docs/compose.md).
- `hivemind node eligibility <id> --disable|--enable`: an ineligible node takes no new replicas, from placement or from a rollout's surge, and keeps the ones it runs. The server stores the flag, so it holds across restarts. `POST /v1/nodes/{id}/eligibility` is the route.
- `hivemind node drain <id> [--deadline 10m] [--no-wait]`: makes the node ineligible, then moves each replica off it with a rollout surge at the replica's own generation, one replica per app at a time, so an app keeps its replica count running while another node has room. A replica with a volume, or one whose host port is taken on every other eligible node, stays, and the drain says why. At the deadline, what is left is stopped and placed again, as on node loss; replicas with a volume keep running. The command waits and prints each move. A drain carries on across a restart of the server. `POST` and `GET /v1/nodes/{id}/drain` are the routes. See [docs/concepts.md](docs/concepts.md#draining-a-node).
- `hivemind nodes` has an ELIGIBILITY column (`eligible`, `ineligible`, `draining` or `drained`), and `GET /v1/nodes` the fields `eligible` and `drain`. Schema version 8 adds the eligibility column and the drain tables; a 2.1 store is migrated when 2.2 opens it.
- HTTPS routing. An app spec can list `routes`, each an exact host and a container port. `serve` and `join` take `--route-addr`, which runs a router on that node on `--route-http-port` (80) and `--route-https-port` (443), with certificates from an ACME CA (`--acme-ca`, Let's Encrypt by default; `--acme-email` is required) for the routed hosts only, over HTTP-01, through certmagic. Any node can run one, and they share certificates, keys, the ACME account and challenge tokens through the server's database, with a lock so that one router issues each certificate. Requests go round-robin to the Ready replicas on any node; a replica that cannot be dialled is skipped for 3 seconds. Port 80 redirects to https with 308. A host belongs to one app: a deploy that claims another app's host gets `409`. Path routes, below, let apps share a host. See [docs/routing.md](docs/routing.md).
- Routed apps publish their route ports on ephemeral host ports of the node's private address, so several replicas of one routed app can share a node, and a rolling update of a routed app starts each new copy beside the old one, on the same node if there is no other. The old copy leaves the routing table when the new one is promoted, and runs 5 more seconds before it is stopped. In the integration test, no request of 4,734 failed during a rolling update through three routers.
- A worker registers the local address of its connection to the server as its private address. `GET /v1/nodes` has `address`, and `GET /v1/routes` shows the routing table. `/metrics` has `hivemind_router_requests_total`, `hivemind_router_upstream_errors_total` and `hivemind_router_cert_expiry_timestamp_seconds` for every router, labelled `node`: the server reads its own router's, and each worker posts its router's every 15 s over the node API (only hosts the server routes are kept, and a report is shown for 2 minutes). Schema version 9 adds the node address, the reported route ports, the route hosts and the TLS storage; `hivemind backup` includes the ACME state.
- `scripts/integration-routing.sh` runs three nodes with routers against Pebble, and CI runs it. Two new fuzz targets cover the node API's routing and TLS storage messages.
- Path routes. A route can have a `path`, a prefix such as `/api`, so several apps can share one host: `www.example.com/api` on one app and `www.example.com/` on another. A request goes to the route whose prefix is the longest one of its path on a segment boundary (`/api` takes `/api` and `/api/x`, not `/apix`), matched on the decoded path cleaned of empty segments, or else to the host's whole host route; with none, it gets `404`. The replica gets the path as the client sent it: nothing is stripped, and there is no `strip_prefix`. A prefix holds letters, digits and `- . _ ~ ! $ & ' ( ) * + , = : @` between single slashes, with no `.` or `..` segment, up to 256 bytes; `%`, `?`, `#`, `;`, spaces, backslashes and anything outside ASCII are refused at deploy. On a host with path routes, the router answers `400` to a path with an encoded slash or backslash, a backslash, a dot segment (also encoded, or as `..;`) or a control character, which an app could read as under another prefix; a host without path routes is served as before. A host and path belong to one app, and a deploy that claims another app's gets `409` naming it. Certificates and metrics stay per host. Schema version 15 replaces the route hosts with routes keyed by host and path. See [docs/routing.md](docs/routing.md#paths).
- A router of a build before path routes gets the routing table it can read: one entry per host, no paths, and no endpoints for a host with a path route, which it answers with `503` rather than send one app's requests to another. This build's router asks the node API for paths. The server logs a warning naming such a router's node, version and hosts, `GET /v1/routes` lists it in `old_routers`, `hivemind routes` names it on standard error, and the status of each app on such a host has a warning. `scripts/integration-mixed.sh` checks what such a router is given, and the warnings. See [mixed versions](docs/routing.md#mixed-versions).
- `hivemind routes` prints the routing table: host, path, app, container port and the ready endpoints of each route. `GET /v1/routes` has `path` in each route, `/` for the whole host.
- `hivemind compose` reads a service's routes from `x-hivemind: {routes: [{host, port, path}]}`, an extension Docker Compose ignores. Any other key in it is refused, and `x-hivemind` at the top level too. See [docs/compose.md](docs/compose.md#x-hivemind).
- `scripts/integration-routing.sh` runs a second app on the routed host under `/v1`, checks through each router which app every path reaches and that the refused paths get `400`, and rolls each app over in turn while requests for `/` and `/v1/x` go through all three routers.
- Private registries. `hivemind registry login <host> --username <name> --password-stdin` (or `--password-file`) stores a credential for a registry, `hivemind registry list` shows each host, username and update time, and `hivemind registry logout <host>` removes one. There is no flag that takes the password on the command line. A node sends the credential to its Docker daemon in `X-Registry-Auth` when it pulls an image from that registry. Docker Hub is `docker.io`, and `index.docker.io` and `registry-1.docker.io` are the same host. The routes are `PUT`, `GET` and `DELETE /v1/registries`, and none returns a password. Credentials are stored in plain text in the server's database, like environment values, are in backups, and reach only the nodes that run an image from that registry. A pull the registry refuses leaves the replica `pending` with a status that names the registry and says to run `hivemind registry login <host>`. ECR tokens last 12 hours and hivemind has no credential helper: run the login again from cron. Schema version 10 adds the `registries` table. See [docs/registries.md](docs/registries.md).
- `scripts/integration-docker.sh` runs `registry:2` with htpasswd and TLS from a CA made for the run, and the integration test pulls from it with and without a login, after a logout, and with a wrong password.
- Versions. A worker sends its hivemind version in a `Hivemind-Version` header on every node API request, and the server stores it at registration and whenever a lease or a report carries a new one. `hivemind nodes` has a VERSION column and `GET /v1/nodes` a `version` field; a node older than 2.2 sends none and shows `-`. Every reply to an authenticated API request carries the server's version in the same header, `GET /healthz` excepted, and `hivemind version` prints it. A log request for a replica on a worker that sends no version and has not polled for log requests since the server started a minute ago gets `worker ... runs a hivemind older than 2.1, which cannot stream logs; upgrade it`. Schema version 13 adds the node version.
- The node API marks its `404` for a node it does not know with a `Hivemind-Error: node-not-registered` header. A worker reads a `404` without it, from a server that sends its version, or a plain-text `404` from any server, as a route the server lacks because it is older, not as "this node is not registered". It logs that once for each feature, as `the server is older than this worker and has no log streaming; upgrade the server` (or lease renewal between status reports, certificate renewal, the routing table), and calls the route again when the server's version changes, or after 10 minutes. Before, a 2.2 worker of a 2.0.0 server logged `this node is not registered with the server: 404 Not Found` every 30 s, and at each renewal check.
- A worker whose address the server refused, as 2.0.0 does, registers it again when a reply shows the server's version changed, and every 5 minutes, so after a workers-first upgrade it takes routed replicas once the server is upgraded, without a restart. `hivemind nodes` has an ADDRESS column.
- The CLI against an older server: `hivemind nodes` shows `-` in ELIGIBILITY when the server sends no `eligible` field, as 2.0.0 does, rather than `ineligible`. `node drain`, `node eligibility`, `registry login`, `list` and `logout`, and `backup --api` turn the server's `404 not found` for a route it lacks into `the server is older than 2.2 and has no node drain; upgrade the server` (2.1 for the backup route), or name the server's version when it sends one.
- `serve` and `join` take an exclusive lock on `<data-dir>/hivemind.lock`, which holds their pid. A second `serve`, `serve --role worker` or `join` on the same directory is refused with `another hivemind (pid N) runs on the data directory ...` before it opens anything. Before, a `serve --role worker` started while `join` still ran was a second agent on the same node.
- On a worker, `init` refuses before it creates anything, and says the machine is a worker of the cluster at the server's address and to run hivemind commands on the server. Before, it refused only at the CA, and left a new `hivemind.db` behind. `init` also checks for a CA before it opens the store. `serve` without `--role worker` on a worker's data directory says to use `--role worker`. A client command on a worker, which has no token, says the same as `init` rather than suggesting `hivemind init`.
- `init` writes the serve flags it is given, such as `--api-addr`, `--api-tls-cert` and `--advertise`, to `<data-dir>/hivemind.yaml`, with mode 0600 and certificate paths made absolute, so the `hivemind serve` that follows uses them. Before, `init --api-addr 10.0.0.5:4483 --api-tls-cert ...` wrote a client config for that address, and a plain `serve` then listened on `127.0.0.1:4483`. `init` refuses the flags, before it creates anything, when the config file exists, as one given with `--config` does. Its last lines name `--data-dir` or `--config` when they were given.
- `hivemind deploy` from flags takes the container's command after `--` (`hivemind deploy --name x --image busybox:stable -- sleep 60`) and named volumes with `--volume name:/path`. An unknown key in an app file is named with its line, where it is and the nearest key, as `line 3: unknown key replica in the app (did you mean replicas?)`, rather than `field replica not found in type spec.App`. [docs/concepts.md](docs/concepts.md#apps-and-replicas) has two app files.
- `scripts/edge-suite.sh` runs real Docker daemons into the failures [docs/failures.md](docs/failures.md) describes: dockerd killed and restarted under the agent, pulls of missing images and tags and from registries that do not resolve, refuse, answer 429 or never answer, full disks on a node and on the server, 20 kills of serve under write load, crash loops, `logs -f` across a server restart, damaged worker data directories, and the largest spec. `test/edgetool` is its stand-in registry and write client. CI runs it weekly and on demand. In its first run, 60,672 writes were acknowledged across the 20 kills of serve, and every one was in the store afterwards.
- Unit tests send 50 concurrent writers through the API for 60 seconds with the race detector, and every spec limit at its value and one past it. `store.CheckInvariants` is the store's own consistency check, which the tests and `edgetool storecheck` run.
- `hivemind deploy --wait` and `hivemind scale --wait` wait until every replica that should run is running and ready at the app's generation, and has stayed so for 3 seconds, printing why a replica waits each time the reason changes. After `--timeout` (default 5 minutes) they print the app's status and exit 1. The README quick start uses them, so the block works when pasted whole, and `scripts/quickstart-check.sh` runs it as written, with no waits of its own.
- A put or a scale says which of the app's replicas no node took, at once. Before, `deploy` of an app whose host port another app publishes on every node, or that asks for more CPU or memory than any node has, or binds an address no node has, returned like any other, and the replicas waited as `pending` until someone ran `status`. The write still succeeds, so that deploying a replacement and then deleting the app that holds the port works, but its reply has `pending`, the first 10 such replicas with the reason `status` shows and, for a host port, the app that holds it (`; held by app api`), `stuck` on the reasons that do not change by themselves, and `pending_count`. `deploy`, `scale` and `compose deploy` print a warning on standard error for each reason and keep their exit status; `deploy --wait` and `scale --wait` exit 1 at once, with the reason, for a stuck replica rather than at their timeout. Older clients ignore the fields. `scripts/quickstart-check.sh` deploys a second app on the quick start's port and checks both. See [docs/concepts.md](docs/concepts.md#placement) and [docs/api.md](docs/api.md#objects).

### Changed

- The router limits its connections. One client address (an IPv6 client's /64) keeps at most 256 open over both ports, `--route-max-conns-per-ip` (0 for none, behind a proxy that does not keep client addresses); the router keeps at most half of the file descriptors its open-file limit leaves after 1,024. A connection over a cap is closed as it is accepted and counted in the new `hivemind_router_connections_refused_total{node,reason}`. An https write that makes no progress for 60 s ends its connection, and an upgraded connection such as a WebSocket that carries no data either way for 10 minutes is closed. Before, nothing limited them: the server's router shares its process, and its file descriptors, with the API, the node listener and the store. [docs/routing.md](docs/routing.md#limits)
- `serve --advertise <name>` chooses the address it binds once, and binds it as an IP. Before, the listeners bound the name's first IPv4 address whether or not this machine had it, and a name whose record still named the old server failed with `bind: cannot assign requested address`. Now that is refused with `--advertise <name> resolves to <address>, and this machine has none of those addresses ...`, which says to give `--cluster-addr`.
- After `serve` starts, a replica whose last report was made to an earlier server process is shown as `unknown`, not as the state it had then, until its node reports again; after a restore on a new machine those containers no longer exist. The same holds for a report from a node that is lost: a volume replica held on a lost node was shown as running and ready, and counted in the status and the metrics, while its node was down. A node that has not reported since the start is `waiting` rather than `lost` until the start grace ends (below).
- An agent that restarts, as in an upgrade, keeps a container that its last report called healthy, and that runs on, healthy and ready, rather than `starting` until its first check passes; before, every routed replica with a health check on a node left the routing table for a few seconds whenever the node's agent restarted.
- A router reads the table and loads the certificates already in the shared storage before it takes TLS connections; before, the first handshakes after a router started failed. A challenge for a host a router has not read in the table yet makes it read the table at once (at most once a second), so a new host's first validation no longer fails on a router that lags the one that ordered the certificate.
- After `serve` starts, the routing table leaves out the server's own replicas as the store had them, and keeps the replicas of workers that were up before the start until they report, for the whole start grace (2 minutes by default). After a restore on a new machine the routers answered `502` for about a second, from the old machine's endpoints.
- A router's connections to replicas fail after 5 s of unacknowledged data (TCP_USER_TIMEOUT on Linux), and a GET, HEAD or OPTIONS request with no body whose connection failed before the reply goes to the next replica. In the router soak, a request sent on a kept connection to a machine that had just lost power waited until the client gave up. `hivemind_router_upstream_errors_total` has a `connection` kind.
- A worker's connections to the server fail after 10 s of unacknowledged data or keep-alive probes (TCP_USER_TIMEOUT on Linux), with a 10 s dial and TLS handshake limit, so a worker whose server machine vanished, or was restored at a new address, stops waiting on a dead pooled connection within 10 s instead of the 30 s request timeout, well inside the 15 s lease.
- Routing reverses part of the v2 scope (decision 2 in [PLAN.md](docs/PLAN.md)), which had host-port networking and no proxy. Host ports work as before, and an app without routes is unchanged, but hivemind now runs a reverse proxy when `--route-addr` is given.
- The router is the one listener that may bind `0.0.0.0`. It has no authentication, because it serves the apps' public traffic. `--route-addr` has no default. Every other listener still refuses a wildcard.
- A worker can read every routed host's TLS private key and the ACME account key over the node API, whether or not it runs a router. [docs/security.md](docs/security.md#what-a-compromised-worker-can-do) lists what that means for a compromised worker.
- Workers older than 2.2 take no routed replicas, because they report no address. A rollout that adds routes to an app moves its replicas off such workers, rather than in place. A 2.2 worker whose server is older registers without its address, as that server's decoder refuses the field. A worker's router needs a 2.2 server.

- A failed image pull backs off: 10 seconds, doubling to 5 minutes, per image and credential. Before, every reconcile pass pulled again. A login or logout changes the credential, so it is tried at the next pass.
- Workers older than 2.2 get no registry credentials. Their decoder refuses unknown fields, so a credential in one assignment would stop them reconciling every replica on the node; a 2.2 worker asks for credentials, and only then gets them. A private image placed on an older worker fails to pull there, with Docker's message.
- An image reference on `index.docker.io` is normalised to `docker.io`, as Docker reads it, so `index.docker.io/nginx` is `docker.io/library/nginx:latest`.
- `hivemind node remove` of a node that is ineligible and runs nothing, as after a drain, needs no `--force`, though the node still renews its lease.
- `serve`, `init` and `join` no longer accept `--server`, and `serve` and `init` no longer accept `--token`. They never used them. `logs` no longer accepts `--json`, which it ignored. Passing one of these flags is now an error. `join --token` is unchanged.
- A client command with `--server http://...` against an API that serves TLS says `the server at http://... speaks https: use --server https://...`, rather than `server returned 400 Bad Request`.
- `hivemind logs` of a replica that has no container yet says it is pending, on which node, and why, as `status` does: `app "web" replica 0 is pending on node node-..., so it has no container to read a log from yet: <the pull error>; hivemind status web shows when it runs`, or `is pending, with no node` and the placement reason. Before, it said `has no container on this node`.
- `hivemind join <host>:4485` is refused at once, before it dials anything, with the reason: 4485 is the default join port, and join takes the cluster port, 4484, or no port, and dials the port above it. Before, the hint came after the 30 s dial timeout.
- The CLI with no token, on a machine where another user set up hivemind, as `sudo hivemind init` does for root, says so and to run the command with `sudo`, rather than to run `init`, which would make a second cluster. It finds out from the files it may not open: the data directory, `/var/lib/hivemind`, the client config and the token file it names.
- `hivemind logs` of a replica past the app's count says which replicas the app has (`app "web" has replicas 0 to 2; it has no replica 7`), rather than that it has no container on this node.
- A volume whose name is a path on the host, as in `--volume /srv/data:/data`, is refused as a bind mount, which hivemind does not support, rather than as a name with the wrong characters.
- `deploy` and `compose deploy` of a spec the app already has say `unchanged`, not `updated`. The reply to `PUT /v1/apps/{name}` has `unchanged: true` then.
- A refused token says where the CLI got it: `--token`, `HIVEMIND_TOKEN`, or the token file the client config names, with a hint to give the other server's token in the last case.
- While a worker cannot reach the server, its passes back off, 2 s doubling to 30 s, and are back at the interval after the first that reaches it. It logs the first failed pass, a line a minute with the count, and one when the server answers again, rather than a warning every pass; the log poll's retries against a server that does not answer are logged at debug level. The lease heartbeat keeps its 5 s timer. The edge suite's new `server-down` case checks it.
- `hivemind join` on a machine whose data directory holds a node that was removed asks that server, with the node's certificate, and says the files cannot be used again: move the directory aside, or use another `--data-dir`, and join again; the token was not used. Before, it said to run `serve --role worker`, which fails for a removed node.
- `serve` logs one line for each schema step it applies to an existing store, as `store schema migrated from=6 to=7 adds="node certificate expiry"`. Before, the migration was silent.
- `hivemind nodes` prints a LEASE AGE of 48 hours or more in days (`123d`), as CERT EXPIRES does, rather than as `2952h0m46s`.
- `serve` and `join` whose user may not open the Docker socket say to add the user to the docker group (`sudo usermod -aG docker $USER`, then log in again) or to run as root. A worker stops at once then, rather than retrying every 5 s, since the group takes effect only for a new login.
- `init` offers `export HIVEMIND_SERVER=...` to another machine only for an API it can reach. For the default loopback API, the line is for another shell on this machine, and a note says how to serve the API to other machines; for a wildcard `--api-addr`, the URL has a placeholder for one of this machine's addresses rather than `127.0.0.1`.
- The server's store has a pool of four read-only connections beside its one write connection. Reads outside a transaction, the API's GETs and the workers' fetches of their assignments among them, run beside the writes, as SQLite's WAL mode allows, and see each commit as soon as it is made. On the scale run a `GET /v1/status` waited 510.6 ms behind 20 deploys in flight.
- A node's status report that is the same as its last one renews the lease and stamps the node's rows with the time, without deleting and inserting them again; a changed report prepares its `INSERT` once. Every report used to rewrite every row, one compiled `INSERT` per container: on the scale run, reports were 30% of the server's CPU and compiling statements 20%. [docs/scale.md](docs/scale.md) has the benchmarks before and after.
- Container logs are rotated. When a node's Docker daemon has the default log driver `json-file`, which keeps a container's output in one file that grows without end, the agent creates each container with `json-file`, `max-size` `10m` and `max-file` `5`, so a chatty app keeps 50 MB of log at most, and `hivemind logs` shows no more than that. These two options replace any `max-size` and `max-file` in the daemon's `log-opts` for hivemind's containers; its other options still apply. With another default driver, such as `local` or `journald`, the daemon's settings are left alone. The driver is read from `/info` at most once a minute. Containers from earlier versions keep unrotated logs until they are replaced. An app without `resources.memory` still has no memory limit, and no app has a PID limit; [security](docs/security.md#apps-on-one-node) says what that means.
- Placement does not run again when nothing it reads has changed since it last ran and placed nothing: the pending replicas and their reasons, the nodes as the scheduler sees them at that moment, and the placed replicas and surges. One replica that no node could take made every sweep and every node's report run the whole placement again. A write transaction also decodes each app generation's spec once, and reads the placed replicas once unless they change.

### Fixed

- The old server, back with its data directory after its cluster was restored elsewhere, ran as a second server of the cluster, with the same CA. In the third acceptance run its router served the old copies of the apps, and a worker that dialled it, as one not yet moved off the old IP address does, would have taken its assignments. The cluster now has an epoch: 0 from `init`, and for a store from before schema version 16, and one more than the backup's after each `restore`, which says so. The server sends it in a `Hivemind-Epoch` header on every node API reply, and logs it at its start. A worker keeps the highest epoch it has seen in `cluster-epoch`, in its data directory, sends it with every request, and refuses a server at a lower epoch: it sends it nothing more, keeps its containers running, logs once at error what happened and what to do, and asks again every 10 s, for the restored server may come back at that address. The old server refuses such a worker with `409`, before it reads its store, and logs once that a newer copy of the cluster exists and that it should be stopped. `hivemind node set-server` refuses it too. A server without the header, from an earlier build, is taken as before. `restore` raises the epoch in the restored store without migrating it; a store from before epochs is left as it is, for the release that wrote it, and gets its epoch from `restored-epoch` when this build's `serve` first opens it. [docs/backup.md](docs/backup.md#if-the-old-server-comes-back) says what the epoch does not cover.

In the third soak the record changed 31 s after the start, nine replicas ran on two machines for 35 s, and 13 of 14 ended on the new server. `serve` now has a start grace, 2 minutes by default (`--start-grace`, at least 15 s): a worker that was up when the server went down, and has not reported since the start, is `waiting` in `hivemind nodes`, not lost, and nothing it runs is placed again. A router restarted more often than every 10 minutes never renewed one itself. A starting router now runs certmagic's renewal check at once when one of its certificates is due.

Each app now records the project that deployed it (the file's top-level `name`, or its directory's name, as Docker Compose takes it), and `compose deploy` refuses an app that `hivemind deploy`, the API or another project deployed, unless `--replace`. Deploying the same file again needs no flag. `PUT /v1/apps/{name}` takes `origin` and `replace` in the query, and `AppView` has `origin`. It now says `the directory /var/backups does not exist; create it first (mkdir -p /var/backups)`, before it reads anything, and says so when the directory is a file.

A pull now goes on in the background once it has taken 2 seconds, the replica's status says `pulling <image>, started <time>; the registry has not answered yet`, a pull that no replica needs any more (the spec was fixed, or the app deleted) is cancelled, and the backoff counts from the end of the pull. Interpolation now makes at most 16 MiB of text for a file and its `.env` together, and past that the file is refused with one problem, `variables make more than 16 MiB of text in this file and its .env`.

They do not: every container is on Docker's default bridge network, and the containers on one node reach each other's container ports at their container addresses, published or not, so a port published on `127.0.0.1` is not private from the other apps on its node. The docs and the reasons now say so, and [security](docs/security.md#apps-on-one-node) has a section on what apps on one node can do to each other.

## [2.1.0] - Unreleased

### Added

- Node certificate renewal. A worker renews its certificate on day 243 of 365, with a new key, over the node API, using its current certificate. The server issues for the node ID in that certificate only, and refuses a removed node or an expired certificate. The new key and certificate are written with mode 0600 and renamed into place, and the worker uses them without a restart. A worker must run 2.1 to renew; a 2.0 worker keeps working against a 2.1 server until its certificate expires.
- The server renews its own cluster listener certificate on the same schedule, without a restart.
- `hivemind nodes` has a CERT EXPIRES column, `GET /v1/nodes` a `cert_not_after` field, and `/metrics` the gauge `hivemind_node_cert_expiry_timestamp_seconds`. Schema version 7 adds the `node_certs` table; a 2.0 store is migrated when 2.1 opens it.
- `hivemind backup <file>`: a backup of the server's store, CA certificate and key, and admin token file, as a tar file with a manifest, a format version and a SHA-256 for each file. It is written with mode 0600, and checked before it is kept. It reads the data directory, with `serve` running or not; `--api` gets it from the new `POST /v1/backup` route instead, which sends it only over TLS or to a loopback client.
- `hivemind restore <file> --data-dir <dir>`: restores a backup into an empty directory, with mode 0700 and files 0600, after checking every digest, the store's integrity and schema version, and the CA. [docs/backup.md](docs/backup.md) has the procedure for replacing a lost server at the same address; the workers reconnect without joining again.
- `hivemind logs` reads replicas on workers, with `--tail` and `-f`. The worker keeps a poll open to the server's node listener, takes the log requests queued for its node, and streams each log back over a request it makes, so it still opens no listener. The server checks the node in the stream's certificate against the request. A worker that does not answer in 10 seconds gets a `504` that names it, a lost node a `503`, and a node with 16 streams open a `429`. Ctrl-C on `logs -f` ends the read on the worker.

### Changed

- Every node API request checks that the client certificate is valid by the server's clock. Before, only the TLS handshake did, so a worker that kept its connection open could keep using a certificate that had expired.
- In the CA's last year, node certificates are issued to end with the CA rather than refused, and the server logs a warning once a day. The CA lasts ten years and cannot be rotated.
- A worker whose certificate has expired fails at start with what to do: remove the node, and join again.
- `node.crt` on a worker is mode 0600 after a renewal; it was 0644.
- `GET /v1/apps/{name}/logs` reads the replica on the node it is placed on, not on the server's node. A replica on a worker no longer gets `404`. Workers of version 2.0.0 do not answer log requests, so their replicas get `504` until they are upgraded.

### Known limits

- The cluster CA cannot be rotated. When it expires, ten years after `init`, every machine must join a new cluster.
- A restored server has the state of the backup: nodes removed since then must be removed again, and join tokens used since then work again until they expire. Volumes on the old server are not in a backup.
- Restoring on a new address is not supported. Workers must join again.

## [2.0.0] - 2026-11-14

Version 2 is a rewrite. It is not compatible with 1.x: the command line, the API, the data directory and the feature set all differ. v1 data is not migrated, so start v2 in a new data directory. See [docs/upgrading.md](docs/upgrading.md).

### Added

- Subcommands: `init`, `serve`, `join`, `join-token`, `deploy`, `status`, `logs`, `scale`, `delete` and `version`.
- Workers. `serve --advertise` opens the node listener (port 4484) and the join listener (port 4485) on that address only. `join-token` issues a single-use token, which lasts 24 hours by default and 168 hours at most. `join` enrolls a machine as a worker and runs its agent in the foreground. `serve --role worker` runs a joined worker after a restart.
- A cluster CA, created by `init`. Node certificates are ECDSA P-256 and last 365 days. A join token carries the CA fingerprint, and a joining machine trusts only that CA.
- Placement across nodes: replicas spread over the nodes, within each node's CPU and memory, and without host-port clashes. A volume pins its replica to its node.
- Node loss: a node whose lease is more than 15 seconds old is lost, and its replicas are placed again. A replica with a volume stays on its node. A returning node removes the containers of replicas that moved away.
- A node takes new replicas 30 seconds after it last became ready (`--min-ready`).
- Rolling updates can surge onto a second eligible node, when that node has the app's host ports free.
- App spec in YAML or JSON, with validation of names, images, ports, volumes, resources and health checks.
- Docker Engine runtime, over the Engine API v1.44: pull, create, start, stop, remove, inspect, list by label, logs and exec.
- An agent on each node that starts, stops and replaces containers to match its assignments. Containers carry the labels `hivemind.app`, `hivemind.replica` and `hivemind.generation`.
- CPU and memory limits. `resources.cpu` becomes the container's `NanoCpus` and `resources.memory` its `Memory`, with `MemorySwap` equal to `Memory` so there is no swap on top. 0 means no limit. The smallest nonzero values are 0.01 CPUs and 6Mi. A container over its memory limit is OOM-killed and restarted with the usual backoff.
- Volumes scoped to their app. Volume `data` of app `web` is the Docker volume `hivemind-web_data`, labelled `hivemind.app` and `hivemind.volume`, so two apps that use the same volume name get separate data. Deleting an app keeps its volumes.
- HTTP, TCP and exec health checks, and restarts with exponential backoff from 1 second to 5 minutes. `status` shows each replica's health, restart count and crash loop.
- Rolling updates: a spec change moves the replicas one at a time. A move waits for its replica to be ready, has a deadline, and pauses the rollout with a reason on failure. Rolling back is deploying the old spec. `status` and the API report an unfinished rollout.
- `init` creates an admin token, stored as a SHA-256 digest. Every API route except `GET /healthz` needs it.
- Prometheus metrics at `/metrics`, and an optional loopback listener for them.
- Logs with `log/slog`, as text or JSON. Tokens, cookies and private keys are redacted.
- Settings from flags, `HIVEMIND_*` variables and a YAML file, in that order of precedence.
- A client config that `init` writes, so the CLI on the same machine needs no token in the environment.
- Command reference in `docs/cli.md`, generated from the command definitions.
- `nodes` lists the nodes, with capacity, lease age, ready or lost, and replica count. `node remove <id>` takes a node out of the cluster: its replicas are placed again, and a replica with a volume waits with no node and a reason. It refuses the server's own node, and a node that still renews its lease unless `--force` is given. The API routes are `GET /v1/nodes` and `DELETE /v1/nodes/{id}`.
- A denylist of removed node IDs, checked on every node API request after the TLS handshake. A removed node's certificate gets 403, the store refuses its ID, and join never issues it again. A running worker that is removed logs it and exits. Schema version 6 adds the table.
- `--ca-cert`, `HIVEMIND_CA_CERT` and a `ca-cert` key in the client config: a PEM file of certificates the CLI trusts for an https API, instead of the system roots. `init --api-tls-cert` records that certificate there.
- `POST /v1/session` and `DELETE /v1/session`: log in with the admin token to get an `HttpOnly`, `SameSite=Strict` session cookie and a CSRF token, and log out. Unsafe cookie requests need the CSRF token. Failed logins are limited to 5 per source address in 10 minutes.
- Release builds for six platforms, and `SHA256SUMS`. The node runs on Linux amd64 and arm64.

### Changed

- The API listens on `127.0.0.1:4483` by default, not on all interfaces.
- Authentication is mandatory.
- The YAML config file refuses a `token` key. Pass the API token with `--token` or `HIVEMIND_TOKEN`, or let the client read the token file that `init` wrote.
- Go 1.26 is required to build. The module declared 1.22 before.
- The SQLite store uses WAL mode, and each change is one transaction.
- `init` and `serve` refuse a v1 data directory and point to docs/upgrading.md.
- `init` creates the cluster CA as well as the admin token.
- Earlier v2 builds named a Docker volume by its spec name alone, so volume `data` was the Docker volume `data`, shared by every app on the node that used that name. It is now `hivemind-<app>_data`, and the first deploy with this build starts with an empty volume. To keep the data: deploy once, so the new volume exists with its labels; run `hivemind delete <app>`, which keeps both volumes; on the app's node, copy the data with `docker run --rm -v data:/from -v hivemind-<app>_data:/to alpine cp -a /from/. /to/`; then deploy again. 1.x is not affected, since v1 data is not migrated.

### Removed

- The web UI, the v1 `/api/` routes, the containerd runtime and the memberlist membership.
- Security (RBAC, secrets, network policy, IPAM, tenants, scanning, storage encryption, ACLs and QoS), resilience (circuit breaker, Redis storage, bulkhead, retry and fallback), service discovery (DNS and proxy), tenants, zero-downtime and canary deployment endpoints, and volume backup and snapshots.

### Known limits

- Node certificates cannot be renewed, and there is no revocation list: removing the node is the only revocation. A certificate lasts 365 days.
- A removed worker's containers keep running until they are removed by hand.
- A replica with a volume is never moved. Its app is down while its node is lost.
- Two apps that publish the same host port are both accepted. The second one's replicas go where the port is free, and any that cannot go stay `pending` with the reason until it is.
- `hivemind logs` cannot read replicas that run on a worker.
- hivemind never deletes a volume. Volumes of deleted apps stay on their node until removed with `docker volume rm`.
- A rolling update on one node replaces each replica in place, so that replica is down while it moves.
- Tests run three nodes in Docker. Larger clusters have not been tested.
