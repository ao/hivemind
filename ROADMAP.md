# Roadmap

Every task in [PLAN.md](docs/PLAN.md) has an implementation, and 2.3.0 added clusters of several servers ([several servers](docs/ha.md)). These are what is left, in suggested order. Each one was checked against the code of 2.3.0.

1. Rolling upgrades of the servers. Every server of a cluster runs the same release: a server will not apply a Raft entry from a leader at another schema version, and a joining server must run the leader's version. So the servers are upgraded together: stop them all, upgrade them, and start them again, while their containers keep running ([compatibility](docs/ha.md#compatibility)). A rolling upgrade would need a leader that writes only entries every server can apply, and a step that moves the schema once all of them run the new release.
2. A CA rotation with more than one server. `hivemind ca rotate start` is refused while the cluster has more than one server, and a server join is refused while a rotation is in progress. Each server keeps the CA files in its own data directory, and a rotation changes them on one machine; carrying the rotation's files and steps to every server is not done. Today a cluster of several servers removes all but one, rotates, and joins the others again.
3. Reads on followers. A follower passes every request but `GET /healthz` to the leader, so the leader carries the whole load of the API and the node API. A follower's router already reads the certificates it serves from the follower's own copy of the store ([the routers' TLS storage](docs/ha.md#the-routers-tls-storage)).
4. The host-port gap in rolling updates. On a single node every move of an app without routes is in place, so each replica is down while its new container starts, whether or not the app publishes a host port. This is closed for routed apps only: an app with `routes` and no host ports publishes its route ports on host ports the agent picks, from 30000 to 32767, so its update starts each new copy beside the old one, on the same node too (see [routing](docs/routing.md#rolling-updates)). The same surge on the replica's own node would close the gap for an app with no host port. Two copies of an app that publishes a fixed host port can't share a node, so such an app keeps the gap on one machine. And a put or a scale lists the replicas no node took, with the app that holds their host port, and `deploy --wait` fails at once for one that cannot get a node by itself (see [placement](docs/concepts.md#placement)), but a change to the spec of an app whose replicas run is not checked that way: its rollout moves each replica later, and a move in place onto a node where another app publishes the new host port has its container refused by Docker there, so the rollout pauses at the move's deadline, and the put's reply said nothing of it. The put could check the new spec's host ports against each replica's node.
5. A web UI, if one is wanted. The API has what a browser needs for Task 6: login and logout at `/v1/session`, a session cookie, and CSRF checks on unsafe requests. There are no pages. A session lives in the leader's memory, so with several servers it ends when the leader changes.
6. Routing beyond exact hosts: wildcard hosts, which need a DNS-01 challenge for their certificates, and TCP routes. Both are refused today. Path prefixes are done (see [routing](docs/routing.md#paths)), and so are HTTP/2 and gRPC to the replicas, over h2c (see [protocols](docs/routing.md#protocols)).
7. The smaller gaps of several servers ([what is not done](docs/ha.md#what-is-not-done)): a dead server stays in the Raft configuration until `hivemind server remove`, so a cluster of three with one dead server tolerates no further loss; and a cluster that drops back to one server keeps running Raft, with one voter.
