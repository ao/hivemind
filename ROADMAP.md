# Roadmap

Every task in [PLAN.md](docs/PLAN.md) has an implementation on this branch. These are what is left, in suggested order. Each one was checked against the code on this branch.

1. Rolling updates of an app that publishes a host port. Two replicas of one app can't publish the same host port on one node, so on a single machine such an app has one replica and its update has a gap. This is closed for routed apps only: an app with `routes` and no host ports publishes ephemeral ports behind the router, and its update starts each new copy beside the old one (see [routing](docs/routing.md#rolling-updates)). An app that publishes a fixed host port still has the gap on one machine.
2. Host ports in a rolling update. A put or a scale now lists the replicas no node took, with the app that holds their host port, and `deploy --wait` fails at once for one that cannot get a node by itself (see [placement](docs/concepts.md#placement)); the write itself is still accepted. A change to the spec of an app whose replicas run is not checked that way: its rollout moves each replica later, and a move in place onto a node where another app publishes the new host port has its container refused by Docker there, so the rollout pauses at the move's deadline, and the put's reply said nothing of it. The put could check the new spec's host ports against each replica's node.
3. The fault suite: a kill of the whole server machine rather than the `serve` process. `scripts/integration-cluster.sh` now destroys the server machine and restores it from a backup, but not under the fault suite's partitions.
4. A web UI, if one is wanted. The API has what a browser needs for Task 6: login and logout at `/v1/session`, a session cookie, and CSRF checks on unsafe requests. There are no pages.
5. Routing beyond exact hosts and path prefixes: wildcard hosts (which need a DNS-01 challenge for their certificates), HTTP/2 or gRPC to the replicas, and TCP routes. Each is refused today. Path prefixes are done (see [routing](docs/routing.md#paths)).
